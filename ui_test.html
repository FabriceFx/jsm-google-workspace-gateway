rocket_launch Guide d'intégration pas à pas

Ce guide vous accompagne, même sans expérience de Jira Automation, pour connecter un formulaire Jira Service Management à Google Workspace. Suivez les sections dans l'ordre : vérifier les prérequis, comprendre le principe, créer la règle Jira, puis tester. Comptez 15 à 20 minutes pour votre première action.

Bon réflexe : avant de toucher à Jira, testez l'action depuis l'onglet Console de Test Interactive (en haut). Si elle fonctionne ici, il ne restera qu'à recopier le payload dans Jira.

checklist 0. Avant de commencer — la checklist

Vérifiez ces points auprès de l'administrateur du script. Sans eux, l'intégration échouera avec un message d'erreur explicite (voir le dépannage plus bas).

✓ Le script est déployé

La webapp Google Apps Script est déployée en « Application Web ». Vous disposez de son URL de déploiement (voir section 3).

✓ Le jeton secret

Un SECRET_TOKEN a été généré et vous a été communiqué. Il authentifie chaque appel Jira. À ne jamais publier dans un ticket.

✓ Les domaines autorisés

La propriété ALLOWED_DOMAINS contient vos domaines (ex. cooperl.com). Une adresse hors de cette liste sera refusée.

✓ Droits & administrateurs

Le compte qui exécute le script est administrateur Workspace, et votre adresse figure dans ADMIN_UI_EMAILS pour utiliser cette console.

✓ Un projet Jira avec Automation

Vous avez accès à Paramètres du projet → Automation dans Jira, avec le droit de créer des règles.

⚙️ Actions e-mail (optionnel)

Les actions Gmail (délégation, absence, transfert) exigent un compte de service configuré. Non requis pour les autres actions.

insights 1. Le principe en une image

À chaque fois qu'un agent fait avancer un ticket, Jira envoie automatiquement un message (un « webhook ») à Google, qui exécute l'action et répond. Vous n'avez rien à faire manuellement dans la console Google Admin.

1. Un agent JSM valide un ticket arrow_forward 2. La règle Jira envoie un webhook (POST) arrow_forward 3. La passerelle vérifie et exécute arrow_forward 4. Google répond, Jira commente le ticket

À retenir : une action = une opération (ex. CREATION_COMPTE). Un groupe d'action (ex. ARRIVEE_COLLABORATEUR) en enchaîne plusieurs dans le bon ordre — pratique pour une arrivée ou un départ en un seul ticket.

dynamic_form 2. Créer le formulaire JSM et ses champs

C'est l'étape en amont de la règle : elle définit ce que l'agent (ou le demandeur) remplit. Le point crucial est le lien formulaire → champ Jira → smart value : sans lui, la règle enverra des champs vides et l'action échouera en MISSING_FIELDS.

① Créer le type de demande

Paramètres du projet → Types de demande → Créer un type de demande. Donnez-lui un nom parlant (ex. « Création de compte Workspace »). Un formulaire vide lui est associé.

② Ajouter les champs au formulaire

Dans l'éditeur du type de demande, glissez les champs nécessaires depuis la bibliothèque (Prénom, Nom, E-mail…). Pour un besoin spécifique, créez un champ personnalisé.

③ Publier

Enregistrez et publiez le type de demande. Il devient utilisable par les agents (et, si voulu, visible dans le portail client).

Le piège n°1 des débutants — le champ « décoratif ».

Si vous utilisez le générateur de Formulaires JSM (Forms/ProForma), un champ de formulaire n'est réutilisable dans l'automation que s'il est relié à un champ Jira. Dans les propriétés du champ de formulaire, activez le lien vers un champ Jira (« Connect to a Jira field » / associer à un champ). Un champ non relié reste dans le formulaire mais n'apparaît pas dans les smart values {{issue.…}} — la cause la plus fréquente d'un data vide.

Trouver l'identifiant d'un champ (customfield_XXXXX).

Deux méthodes : (a) dans la règle d'automation, cliquez sur « Insérer une smart value » et cherchez le champ — Jira insère la bonne référence ; (b) côté admin, Paramètres → Champs → Champs personnalisés, ouvrez le champ : son numéro figure dans l'URL (…customFieldId=10001 → customfield_10001). Les champs système (Résumé, Rapporteur…) s'écrivent par leur nom ({{issue.summary}}).

Exemple bout-en-bout — action CREATION_COMPTE

Le catalogue (section 6) indique que cette action attend prenom, nom, email_souhaite (+ champs optionnels). On crée donc un champ de formulaire pour chacun, relié à un champ Jira, puis on les mappe dans le payload :

Champ du formulaire JSM Champ Jira relié Clé data de l'action Smart value dans le payload
Prénom customfield_10101 prenom {{issue.customfield_10101}}
Nom customfield_10102 nom {{issue.customfield_10102}}
E-mail souhaité customfield_10103 email_souhaite {{issue.customfield_10103}}

Les identifiants 10101… ci-dessus sont des exemples : remplacez-les par ceux de votre instance. Le data final ressemblera alors à celui pré-généré pour vous en section 6.

Le chaînon complet : Formulaire JSM (ce que l'humain remplit) → Champ Jira (customfield_XXXXX) → Smart value {{issue.…}} → clé data du payload → action de la passerelle. Une fois ce lien en place pour chaque champ, la règle (section 3) n'a plus qu'à transporter le tout.

build 3. Créer la règle dans Jira Automation

Dans votre projet Jira : Paramètres du projet → Automation → Créer une règle. Puis configurez les trois briques suivantes.

① Le déclencheur (Trigger)

Ce qui lance la règle. Choisissez « Transition de ticket » (ex. passage à « Approuvé ») ou « Ticket créé ». C'est le moment où l'action doit partir.

② L'action « Send web request »

Ajoutez une action « Envoyer une requête web ». Méthode : POST. En-tête : ajoutez Content-Type = application/json. Cochez « Attendre la réponse » pour pouvoir commenter le ticket ensuite.

③ Le corps (Web request body)

Choisissez « Custom data » et collez le payload JSON (section 4). C'est là que vous mettez le jeton, le nom de l'action et les champs.

L'URL à coller dans « Webhook URL / URL »

Copiez cette URL exacte (c'est l'adresse de la passerelle) et collez-la dans le champ URL de l'action web :

Ouvrez ce guide depuis l'URL du déploiement pour afficher l'adresse exacte.

data_object 4. Le message à envoyer (payload JSON)

Le corps de la requête est un objet JSON à quatre parties. Voici le modèle ; adaptez les valeurs entre accolades.

{
  "secret_token": "VOTRE_SECRET_TOKEN",
  "action": "NOM_DE_L_ACTION",
  "ticket_key": "{{issue.key}}",
  "request_id": "{{issue.key}}-{{now.epochMillis}}",
  "data": {
    "champ_1": "{{issue.customfield_10001}}",
    "champ_2": "{{issue.customfield_10002}}"
  }
}

secret_token

Le jeton fourni par l'administrateur. Il prouve que la requête vient bien de Jira. Sans lui : erreur FORBIDDEN.

action

Le nom exact de l'opération, en MAJUSCULES (ex. CREATION_COMPTE). La liste complète est en section 6.

ticket_key / request_id

Laissez {{issue.key}} tel quel : Jira le remplace par la référence du ticket. Le request_id évite les doublons si Jira réessaie.

data

Les informations métier (e-mails, nom, groupe…). Chaque action a ses propres champs : voir la section 6, qui génère le bon data pour vous.

Qu'est-ce qu'un « smart value » comme {{issue.customfield_10001}} ?

C'est un espace réservé que Jira remplace, au moment de l'envoi, par la valeur du champ du ticket. Pour trouver l'identifiant d'un champ personnalisé : dans la règle Jira, cliquez sur « Insérer une smart value », ou consultez Paramètres → Champs personnalisés. N'utilisez pas le libellé français du champ (« Prénom ») mais bien sa référence technique (customfield_XXXXX).

call_split 5. Que faire de la réponse de Google

Après l'action web, ajoutez dans la règle des branches selon {{webResponse.body.status}} pour informer l'agent sur le ticket.

status = "success" (HTTP 200)

Action exécutée. Ajoutez un commentaire public au ticket avec {{webResponse.body.message}}, puis passez le ticket à « Résolu ».

status = "queued" (HTTP 202)

Demandé hors créneau : la passerelle l'exécutera automatiquement au prochain créneau. Commentaire d'info : {{webResponse.body.message}} (contient la date prévue).

status = "error"

Une anomalie a empêché l'exécution. Commentaire interne avec {{webResponse.body.error_code}} et {{webResponse.body.message}}, puis assignez au support N2. Voir le dépannage ci-dessous.

Astuce : le champ trace_id de la réponse identifie l'exécution côté Google. Reportez-le dans le commentaire d'erreur : il permet à l'IT de retrouver la trace exacte dans le journal.

view_list 6. Catalogue des actions & payloads prêts à copier

Cliquez sur une action pour voir ses champs et copier son payload JSON déjà pré-rempli avec les bons noms de champs. Il ne vous restera qu'à remplacer les valeurs par vos smart values Jira.

healing 7. En cas de problème (dépannage)

Le code d'erreur renvoyé (error_code) indique précisément la cause. Les plus fréquents :

Code Cause probable Que faire
FORBIDDEN Jeton absent ou incorrect. Vérifier que secret_token du payload correspond exactement au jeton fourni.
MISSING_FIELDS Un champ obligatoire est vide. Le message liste les champs manquants. Vérifier le mapping des smart values dans la règle Jira (champ vide côté ticket ?).
INVALID_EMAIL Une adresse est mal formée. Souvent un champ Jira vide ou contenant autre chose qu'une adresse. Vérifier la valeur envoyée.
DOMAIN_NOT_ALLOWED Domaine hors liste blanche. L'adresse n'est pas dans ALLOWED_DOMAINS. Corriger l'adresse ou demander l'ajout du domaine à l'IT.
UNKNOWN_ACTION Nom d'action inconnu. Vérifier l'orthographe exacte (MAJUSCULES) du champ action. Liste en section 6.
NOT_FOUND Compte ou groupe introuvable. Vérifier l'adresse cible : orthographe et domaine exacts tels qu'en console Admin.
NOT_CONFIGURED Prérequis manquant côté script. Typiquement une action Gmail sans compte de service, ou une licence sans LICENSE_SKU_ID. À traiter par l'IT.
GROUPE_PARTIEL Un groupe d'action a partiellement échoué. Le message détaille chaque étape (OK / ÉCHEC). Relancer la règle réessaiera les étapes en échec (les réussies sont ignorées).
Méthode conseillée : reproduisez d'abord l'erreur dans l'onglet Console de Test Interactive avec les mêmes valeurs. Vous verrez le code d'erreur immédiatement, sans dépendre du délai de Jira.

menu_book Glossaire express

Webhook

Un message HTTP envoyé automatiquement d'un système à un autre. Ici : de Jira vers Google.

Payload

Le contenu (JSON) du message envoyé : jeton, action et données.

Smart value

Espace réservé {{...}} que Jira remplace par une vraie valeur du ticket à l'envoi.

Champ personnalisé

Champ propre à votre projet Jira, identifié par customfield_XXXXX.

OU (unité organisationnelle)

Dossier de classement des comptes dans Google Admin. Commence toujours par /.

Fenêtre Standard / Permanente

« Standard » = exécuté aux heures ouvrables (sinon mis en file). « Permanente » = 24/7, pour la sécurité.

SKU de licence

Identifiant d'une édition Workspace (ex. Business Standard), pour attribuer/retirer une licence.

trace_id

Identifiant unique d'une exécution, à communiquer à l'IT pour retrouver la trace côté Google.
